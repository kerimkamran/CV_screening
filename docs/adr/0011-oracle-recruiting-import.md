# 0011 — Read-only CV import from Oracle Recruiting, ahead of R4

Status: **Proposed** on 20 November 2026. NOT accepted yet. The programme owner accepts it by changing this line. Until then no Oracle schema or product code merges: this ADR is the entry gate for Phase 2 of `docs/stage-3/development-plan.md`, the first Oracle schema. The Phase 0 probe script (`scripts/oracle-probe.mjs`) is not held by this gate: Phase 0 starts on the owner's go, and the probe sits outside the product, reads one synthetic vacancy on the Oracle test environment and prints counts only. The bulk-upload fixes (Phase 1) do not depend on it.

## Context

- ADR 0002 (D2) says "No ATS/HCM integration before R4". ADR 0010 lists "Oracle HCM integration" under "Not built".
- On 20 November 2026 the programme owner asked for one part of that integration now: a recruiter adds an Oracle vacancy ID to a Parallax vacancy, and Parallax copies that vacancy's CVs from Oracle. Today a CV file enters Parallax only when a recruiter uploads it in the browser.
- Why it can come before R4: it only reads, and it feeds the intake path that uploads already use, so every rule built for uploads applies to an imported CV unchanged. Writing anything back to Oracle is not in scope and stays in R4.
- What exists today (checked on `main` at commit d18f81b, 20 November 2026):
  - `vacancy.external_ref`, described in the schema as the "optional slot for the eventual Oracle HCM requisition key (R4)", with a unique index per organisation (`db/migrations/0001_core_schema.up.sql:32-38`). Nothing reads or writes it. Outside the Stage 3 plan it is named only in that migration and in ADR 0002.
  - Bulk upload is already built (Stage 2, migration 0036): several files, a folder, drag-and-drop and ZIP, with a per-file status kept on the server and a retry. One service takes every CV (`apps/api/src/pipeline/intake.service.ts`).
  - There is no Oracle code, no OAuth client code and no shared outbound HTTP client. The folder `apps/api/src/integrations/` does not exist yet.

## Decided by the programme owner

All taken on 20 November 2026 and recorded in `docs/decisions.md` (section "Stage 3").

- **Product:** Oracle Fusion Cloud HCM, Oracle Recruiting.
- **Access:** direct REST calls from the Parallax backend. No middleware.
- **Volume:** 100 to 500 CVs per Oracle vacancy.
- **Trigger:** on demand. Import, then Refresh later for what is new. No scheduled polling.
- **Which applicants:** active only (confirmed, not withdrawn, not disqualified).
- **Hosting at go-live:** Render Frankfurt, the current trial host (ADR 0010).
- **Who may link:** any recruiter who can edit a vacancy may link it to an Oracle vacancy, audited, with no approval step. The security review rated this risk critical. The owner accepts it on three compensating controls (first row of "Controls").
- **Confirmation:** once up front, on Oracle's estimate. The import pauses again only on exceptions.
- **Set-up:** super simple. An admin pastes the Oracle API address, user name and password into one form in the admin panel and clicks **Activate**. No server configuration per connection.
- **Where it can be activated:** only where the deploy switch `ORACLE_IMPORT_ENABLED` is set (production).

## Decision

How it is built. The detail is in sections 3 and 5 of the plan.

1. **Read-only.** Parallax reads the Oracle vacancy, its applications, their attachment details and the CV files. It writes nothing to Oracle.
2. **Same intake path.** Every imported file enters through `IntakeService.admit`, so the duplicate check, the 500-CV limit, the notice and frozen-criteria gate and the audit apply unchanged. There is no second insert path.
3. **In-process, lease-based runner.** One Import or Refresh is one `import_run`, worked by a runner modelled on `ProcessorService` (`SKIP LOCKED`, 120-second lease). No new queue service and no separate worker (Stage-2 decision #1, "no architecture replacement").
4. **List, then fetch.** The run first reads the list of applications, then fetches the files two at a time. The recruiter confirms once on Oracle's estimate. The run pauses again only if the exact count is above the estimate or above the room left in the vacancy. Each run that fetches a file makes one upload batch with `source = 'oracle_hcm'`.
5. **One Oracle vacancy to one Parallax vacancy.** The existing unique index on `vacancy.external_ref` stays.
6. **The actor is the recruiter who clicked.** Their roles are re-loaded from the database and the upload gate is re-run for every file. No anonymous service user uploads. Access control (ADR 0009) is unchanged.
7. **Hashed identifiers.** Oracle's numbers for applications and attachments are kept only while a run is active. When it ends, only keyed hashes of the application, the attachment and the person remain (HMAC under a dedicated, versioned key). The Oracle vacancy number is the exception: it stays on the vacancy and in the audit trail.
8. **Tombstones.** Erasing a candidate writes a hashed tombstone (per application, and per person and vacancy) into an append-only table. A later Refresh skips anything on that list.
9. **Least data.** No names or e-mail addresses are requested from Oracle. Identity still comes from the CV text, as for uploads. Applications that are left out are kept as counts only.
10. **One-form Activate.** Activate checks the address, stores the password encrypted (`SettingsCrypto`, new table `integration_connection`), makes one test call and switches the integration on if the call passes. Because a person types the address (AI endpoints are fixed in the server, ADR 0010), the server accepts it only if it is `https`, the host ends in `.oraclecloud.com` and it resolves to a public address. It never follows a redirect to another host.
11. **Sign-in to Oracle.** User name and password by default: that is what the simple form asks for. OAuth sits under "Advanced" for the case where the Oracle team does not allow a password. There is no automatic fallback between the two.
12. **Activation only where `ORACLE_IMPORT_ENABLED` is set.** The switch is set on the production service and nowhere else. Everywhere else the form says "not available in this environment". Tests use a fake Oracle that runs inside the test process.
13. **Three settings only, none per connection:** `ORACLE_IMPORT_ENABLED`, `IMPORT_TOMBSTONE_KEY` and `DB_SIZE_LIMIT_MB`. Concurrency, call rate and the Refresh cooldown are code defaults.
14. **No scheduled polling.** Every Refresh re-checks which imported applications have gone from Oracle. A reminder appears after 30 days without a Refresh.

Still to confirm on the Oracle test environment, with a probe that reads one synthetic vacancy and prints counts only: which sign-in mode works, how a file is downloaded, the exact form of the list query, whether the "vacancy ID" recruiters use is Oracle's requisition number, and that Azerconnect's Oracle address fits the address rule in point 10.

## What this supersedes and what it does not

- It supersedes one sentence of ADR 0002, "No ATS/HCM integration before R4", for one scope only: the read-only import of CVs from Oracle Recruiting into a Parallax vacancy.
- It does not cover writing anything back to Oracle (scores, decisions, moves between stages). That stays in R4. It covers no other ATS or HCM system.
- ADR 0002 also says the architecture is integration-ready through "the outbox/event schema (INTG-02/03, S4–S8)". Checked on 20 November 2026: migrations 0001 to 0039 in `db/migrations` create no outbox table and no event table for integration. The only event table is `audit_event` (migration 0002), which is the audit trail. This import only reads, so it does not need an outbox and does not add one. INTG-02/03 are still to be built for R4.
- ADR 0010 (line 36) lists "Oracle HCM integration" under "Not built". That stays true until this import ships. After that, read it as "writing back to Oracle".
- ADR 0010 (line 8) says of AI models: "Endpoints are fixed in the server (no administrator-typed addresses)." That rule is about AI endpoints and stays as it is. The Oracle connection departs from it on purpose: an administrator pastes the Oracle address (owner decision of 20 November 2026, "Set-up" above). The compensating control is the address rule in point 10 of "Decision": `https` only, a host ending in `.oraclecloud.com`, a public address only, and no redirect to another host.

## Relation to ADR 0010 and the live-data rule

- The working agreement says "No live candidate data before all 21 R1a gates close (D3)" and "No resource outside westeurope/northeurope (PLAT-09)". The trial runs with real candidates on Render Frankfurt only through the owner's exception in ADR 0010 and `docs/mvp-trial-compliance.md`. That exception covers CVs that recruiters upload.
- A pull of live applicants from Oracle is a new flow. **OPEN:** it needs the programme owner's written extension of the trial exception (a signed row in `docs/decisions.md`) and the DPO's sign-off on section 6 of `docs/dpia-fria-draft.md`.
- This ADR does not grant that exception. Accepting it lets code merge. It does not let live Oracle data move.
- The gate is the deploy switch. `ORACLE_IMPORT_ENABLED` is set on the production service only after this ADR is accepted and both documents above exist, and that is recorded in `docs/deploy-render.md`. Until then the Activate form is not available.
- Nothing here relaxes the residency guard or rewords D3 or PLAT-09.
- Staying on Render has two consequences. `render.yaml` declares no fixed outbound address, and the plan records Render's outbound addresses as regional ranges shared with other Render customers: a problem if Oracle's security team requires a list of allowed caller addresses. And capacity stays bound by Stage-2 decision #18 (current plans only, starter and basic-256mb, no automatic upgrade).

## Before it is switched on

All of these, in writing where it says so (plan section 8, and Phases 0, 5 and 6 in section 9):

1. This ADR is accepted.
2. **OPEN:** a row in `docs/decisions.md`, signed by the programme owner, extends the trial exception to the Oracle flow on Render Frankfurt.
3. **OPEN:** the DPO signs off section 6 of the DPIA draft.
4. The Oracle team confirms in writing that the integration account is limited to the organisations in scope and that confidential vacancies are excluded.
5. The probe report from the Oracle test environment is in, and the sign-in mode and download method are chosen.
6. Gates G-11 (peak memory at or below 85 % with no out-of-memory restart during a 500-CV import) and G-12 (database disk at or below 70 % afterwards) pass on a temporary copy on the current plans, or the owner decides (Stage-2 decision #8).
7. Retention is on. The antivirus decision is recorded. Network access from Render to Oracle is confirmed. The runbook is written.

Then: `ORACLE_IMPORT_ENABLED` is set on the production service, an admin pastes the address and the account and clicks Activate, and the first import runs on one agreed vacancy as a pilot.

## Risks accepted knowingly

- **Open linking.** No approval step before a recruiter links a vacancy. The three controls above are mandatory, and the first one depends on the Oracle team.
- **No polling.** A withdrawal or removal in Oracle is not seen until the next Refresh. Only the reminder and retention bound it.
- **Hashes are kept.** The hashes of Oracle application and person numbers stay as pseudonymous data. The DPO sets for how long.
- **No antivirus** on any path, browser upload or import.
- **Disk room.** On the current plan a 500-CV import may be refused (the Stage-2 estimate for one full vacancy is about 750 MB). The import stops before copying anything.
- **The 21 R1a gates are not listed anywhere in the repository**, so their closure cannot be shown from it.
