# Deploying to Render

One Render web service (the API also serves the web app) plus one Postgres database, both in Frankfurt.
No Docker daemon is needed on your machine; Render builds `docker/render.Dockerfile`.

## 1. Push and create

> **Use the Blueprint (or Runtime: Docker).** If you create the service by hand with the default "Node"
> runtime, Render runs `npm install`/`npm run build`/`npm run start`. That now works (`npm start` migrates and
> starts the API), but poppler is not installed there, so PDF CVs cannot be read and go to manual review.
> If a deploy failed with `Missing script: "start"`, either pull this version, or delete the service and create it
> from the Blueprint. A hand-made service must have Language = Docker and Dockerfile Path = `docker/render.Dockerfile`,
> and the environment variables listed in `render.yaml`.

1. Push this repository to GitHub (`kerimkamran/CV_screening`).
2. Render dashboard → **New → Blueprint** → pick the repository. Render reads `render.yaml` and proposes the database and the service.
3. When asked, fill the variables marked `sync: false`:
   - `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD`: the first administrator. The password is temporary; it must be changed at first sign-in. Use 12+ characters.
   - `APP_BASE_URL`: the service's public URL, e.g. `https://cv-screening.onrender.com` (set it after the first deploy if you do not know it yet, then redeploy). It goes into the emailed sign-in link.
   - `EMAIL_FROM` and `RESEND_API_KEY`: see "Email" below.
4. Deploy. On start the container runs the migrations, creates the least-privilege database role if Render allows it, and starts the API. Check the service log for `bootstrap admin created` and `API will connect as least-privilege role cv_api`. If you instead see `WARNING: could not create the least-privilege role`, the API runs as the database owner; that is functional but weaker (see ADR 0010).

## 2. First use

1. Open the URL, sign in as the bootstrap admin, choose a new password.
2. **Admin → AI models**: three steps in one form.
   - **1. Company**: Google, OpenAI, Anthropic, Z.ai, Sakana Fugu or NVIDIA. A short note under the choice says where that company processes data.
   - **2. Model**: the company's documented models are listed straight away. After you type the key, **Load all <company> models** asks the company itself which models your key can use (Sakana and Z.ai may not offer a live list: then the documented models stay, and you can type any other model ID). Tick one or more.
   - **3. API key**: paste ONE key per company; it covers all of that company's models. Extra options appear only where a company needs them (OpenAI: optional "Europe" data region, valid only for a project created with EU data residency).
   - Press **Save company and model**, then **Test** and **Use this** on the model you want. **Use this** runs a test call first and switches only if it works. Switch to any other model or company whenever you like; each assessment records the company and model that produced it.
   - To add more models to a company that already has its key, pick the company again: the key shows as "on file" and you only tick models.
3. **Admin → Users**: add recruiters. Each gets an email with the sign-in address, a temporary password and a one-time invitation link. If email is not set up or fails, the page shows the **invitation link to copy**: send it by any channel (Teams, WhatsApp, in person). The person opens it, chooses their own password and is signed in. A link has no time limit and works once. **Copy invite link** on any user makes a new one (for a first invitation or a forgotten password) and withdraws the previous unused link. No password is ever shown on screen.
4. A recruiter creates a vacancy, extracts criteria, edits and freezes them, confirms the candidate notice, uploads CVs, reviews, decides, exports.

## Email

Render's free web services block outbound SMTP, so the default is **Resend** over HTTPS (works on every plan):
create a Resend account, verify your sending domain (e.g. azerconnect.az) or use their test sender, create an API key, and set
`RESEND_API_KEY` and `EMAIL_FROM` (`parallax by Azerconnect Group <no-reply@azerconnect.az>`). For SMTP on a paid plan set
`EMAIL_PROVIDER=smtp` and the `SMTP_*` variables. If email is not configured or fails, creating a user still works: the admin copies the one-time invitation link (shown once) and sends it themselves.
The link is built from the address you are using, so open the admin pages on the service's real URL (not a preview address) when copying links. `APP_BASE_URL` only affects links inside emails.

## Operations

- **Secrets**: `SESSION_SECRET` and `SETTINGS_ENCRYPTION_KEY` are generated by Render once. Never change `SETTINGS_ENCRYPTION_KEY` (the stored provider keys would become unreadable; you would re-enter them).
  If you created the service by hand (not from the Blueprint), add `SETTINGS_ENCRYPTION_KEY` yourself: Environment → Edit → the arrow next to _Add variable_ → _Generated secret_, name it `SETTINGS_ENCRYPTION_KEY`, then _Save, rebuild, and deploy_. Any generated value of 32+ characters works. Without it the app cannot store AI keys and shows "SETTINGS_ENCRYPTION_KEY is not configured".
- **Backups**: use a paid Postgres plan (the free one expires after 30 days) and enable its backups. CVs are stored in the database.
- **Scale**: keep one instance (the screening queue runs inside the API process).
- **Logs**: structured JSON; CV text is never logged. Each response carries `x-correlation-id`.
- **Rotate a key**: Admin → AI models → the company → Key and settings → Replace API key → Save. **Remove company** deletes its key and models; if one of them was active, no model is active until you choose another.
- **Disable a user**: Admin → Users → Disable (their session stops working on the next request).

## Stage 2 release notes for the operator

Deploy `stage2` only when the owner decides to (the branch is not merged into `main`).

- **Migrations 0035 to 0039 run on start**: upload batches (0036), worker lease (0037), Word pages (0038, which marks every live Word CV as waiting so its pages are made after the deploy) and download tickets (0039). They are additive; `npm run db:rollback` undoes them one by one.
- **The image now carries LibreOffice Writer** (headless, no GUI) and metric-compatible fonts, so Word CVs are shown as their own pages. It makes the image larger (a few hundred MB; not measured here, as no Docker build ran in this workspace) and the first build slower. Check the start log for `Word pages: LibreOffice ...` and `Memory limit: ... MB`. If the log says `LibreOffice ... was not found`, Word CVs are shown as text only; nothing else is affected. The converter runs one file at a time, never while uploads are being read and never above 60 % of the memory limit; set `RENDITION_ENABLED=false` to turn it off entirely.
- **New setting** `DOWNLOAD_MAX_CONCURRENT` (default 2): ZIP downloads streamed at once; a further one waits its turn.
- **Download links** look like `/downloads/<token>`: single use, valid for two minutes, and the token is replaced by `[token]` in the request log.
- **The OPS0 spike is still open**: measure LibreOffice on the real Render plan (memory peak and time for the hostile and the large fixtures) before UAT; if it is not safe there, the owner decides (decision #8).
- **Who may change a vacancy**: every recruiter and team lead, for every vacancy they can see (owner decision, 21 Oct 2026). Set `VACANCY_EDIT=owner` to go back to "only the owner or a team lead".

## Stage 3 release notes for the operator

**Phase 1, bulk upload (ships on its own).** Migration `0040_upload_cancel` adds the "Stop sending files" columns and, on its first run, scrubs the file name of every CV that was erased before it: the name becomes `erased` and only its SHA-256 is kept (`cv_document.erased_name_sha`), on `cv_document` and on its `upload_item` rows. This cannot be undone by the down file (it drops the columns only). It runs in seconds on today's data. Nothing else changes for the operator; uploads now hold at most 500 files per batch and a ZIP is read from a temporary file, so the instance needs free temp space of the largest ZIP (100 MB) plus 64 MB.

**Phases 2 to 4, Oracle import (dark).** No Oracle code merges to `main` before ADR 0011 line 3 reads "Accepted" (the guard test `S3-OPS-01` in `scripts/__tests__/guards.test.mjs` fails until then). The first Oracle deploy adds migrations 0041 and 0042 (they only add; `lock_timeout` 10 s) and three settings, declared in `render.yaml`:

| Setting                 | Value                    | Note                                                                                                                                                |
| ----------------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ORACLE_IMPORT_ENABLED` | `sync: false`, not set   | The deploy switch. Set by hand on `cv-screening` only, at go-live (step 9 below). Off: every Oracle route answers 404 and the runner claims nothing |
| `IMPORT_TOMBSTONE_KEY`  | generated by Render once | **Never change, delete or copy it.** Without it erased candidates can come back on Refresh. Rotation: runbook section 18                            |
| `DB_SIZE_LIMIT_MB`      | the database disk in MB  | An import is refused before copying when the projection passes 70 % of it. Confirm the plan's disk size and write it here: ______ MB                |

After each dark deploy check: the boot log shows the migrations and "API will connect as least-privilege role cv_api"; `/readyz` answers 200; one file uploads; every Oracle route answers 404; no Oracle field shows to a recruiter or an admin.

### Switch-on and the pilot

1. Every line above is signed except line 13. A working morning outside Oracle's maintenance window, the Oracle contact reachable, no upload running.
2. Set `ORACLE_IMPORT_ENABLED=true` on `cv-screening` in the Render dashboard, and nowhere else. Who: ______ When: ______.
3. The boot log has no "Invalid environment configuration" line. The **Oracle import** tab shows in Administration.
4. The admin pastes the address, user name and password, ticks the box and clicks **Activate** once. Expect "Active. Signed in to Oracle, and the account can see vacancies." Any other line: runbook sections 5 to 8. Enter the password expiry date under Advanced; review and sign line 13.
5. Pilot: the recruiter types the Oracle vacancy ID, reads the Oracle title in the dialog and clicks Start. Watch the run list, the Render memory graph (at or below 85 %), the database disk (at or below 70 %), the log for `import.stalled` and HTTP 5xx, the count lines summing to the listed total, and one browser upload to another vacancy going through.
6. When it finishes: Download report opens; a Refresh copies 0 files and starts 0 analyses; the audit trail has the link, the confirmed estimate, the exact count and one upload row per file.
7. Pilot record (no names): date ______, people ______, applications ______, copied ______, minutes listing/fetching ______, peak memory ______ %, disk ______ %.

### Rollback, mildest step first

1. Admin: Abandon any active run, then Turn off. No deploy needed.
2. Operator: remove `ORACLE_IMPORT_ENABLED` on `cv-screening`. Leave `IMPORT_TOMBSTONE_KEY` in place. At the next start active runs are cancelled, their open files closed and their raw Oracle numbers blanked; imported CVs stay ordinary CVs.
3. Image rollback (only for a fault outside the import): steps 1 and 2 first, then Render → Deploys → roll back. The schema stays; the older image starts on it. While it is live, an erase writes no tombstone; after rolling forward the next Refresh still withholds that person (an import item whose CV was erased counts as withheld).
4. Never: `npm run db:rollback` to or past 0041 on production; deleting or regenerating the tombstone key; a database restore without the DPO's decision afterwards (it loses tombstones and erasures made since).
