# Oracle import: what Parallax will do, what we need from you, and our questions

**For:** the team that runs Azerconnect's Oracle Fusion Cloud HCM (Oracle Recruiting).
**From:** the Parallax team. Parallax is Azerconnect's AI CV screening tool.
**Date:** 20 November 2026. **Status:** a description of what we intend, and questions. Nothing is built yet and nothing connects to Oracle yet.

Today recruiters upload CVs into Parallax by hand. The owner of Parallax has asked for a second way: the recruiter types an Oracle vacancy ID into a Parallax vacancy, clicks **Import CVs from Oracle**, and Parallax copies that vacancy's CVs through Oracle's REST API. Oracle calls a vacancy a _job requisition_; this note uses both words for the same thing. The full design is in `docs/stage-3/development-plan.md`. Where this note and the plan differ, the plan wins.

**Not approved for live applicants yet.** Parallax runs today as an internal trial on Render in Frankfurt, under a written exception that covers CVs uploaded by recruiters (ADR 0010). A copy from Oracle is a new data flow, and that exception does not cover it. This note grants nothing and changes none of the project's rules on live candidate data and hosting region (D3, PLAT-09). Before Parallax may connect to your production environment, the following must exist in writing. All four are **OPEN** today:

- The **programme owner** accepts ADR 0011, the project's written decision to build this import. Today it is only proposed.
- The **programme owner** signs the decision that extends the trial exception to this data flow (the open row in `docs/decisions.md`).
- The **DPO** signs off the new data-protection (DPIA) entries.
- **You** confirm in writing that the integration account is limited as described in section 2.

The other go-live conditions (retention switched on, a decision on antivirus scanning, network access confirmed) are in the plan, section 9, Phase 6.

## Update, 23 November 2026: what changed after the Oracle developer review

Parallax was checked against Oracle's REST documentation and changed in five places. Questions 4, 5, 14 and 17 still stand, but the answers no longer need code changes:

- **Files** are read through the attachment's documented FileContents download (`…/child/attachments/{key}/enclosure/FileContents`), addressed by the attachment's own `self` link, as Oracle asks a client to do. The `FileUrl` link and the inline `FileContents` field remain as fallbacks the administrator can choose under Advanced. Please confirm the account may read attachment contents this way (question 7).
- **CV categories** are compared without case, spaces, hyphens or underscores, and the default list adds Oracle's resume code. Under Advanced, **Find the category names Oracle uses** reads up to 20 applications of one vacancy and shows only category names and counts, so the administrator can add the right values (question 14).
- **OAuth JWT assertion** is now supported (RS256, the certificate alias as `kid`, the documented claims). The client signs in with its secret, or with a client assertion signed by the same key (question 5).
- **Your own domain**: if Oracle is reached through an Azerconnect domain instead of `*.oraclecloud.com`, the operator lists that host on the server (`ORACLE_OWN_HOSTS`). The admin form cannot add one (question 2).
- **CVs only on the candidate profile**: an Advanced setting, off by default, reads the candidate profile (`recruitingCandidates`, finder `findByPersonId`, field `CandidateNumber` only) when an application has no CV file. Switching it on adds one candidate lookup per such application (questions 16 and 17). Until it is switched on, the statement below that Parallax makes no call to the candidate resource still holds.

## 1. What Parallax will do

- **It only reads.** Every call to your data is a read (HTTP GET). Parallax never creates, changes or deletes anything in Oracle. If you ask us to sign in with OAuth, there is one extra sign-in call to get a token; it changes no data.
- **It calls only when a person clicks.** There is no scheduled job. Calls happen when a recruiter looks up a vacancy ID, clicks **Import** or clicks **Refresh**, and when a Parallax administrator clicks **Activate** or **Test again** (one small test call, at most once every 5 minutes).
- **It is slow on purpose.** At most two calls at once and about four calls a second. Refreshes are at least 10 minutes apart. There is a daily ceiling on calls (the number is not set yet; see question 13). If Oracle is busy or down, Parallax waits, follows Oracle's `Retry-After` value, and tries again later for up to 2 hours. If sign-in fails, it stops at once and does not try again, so the account is not locked.
- **Size of one import.** The owner expects 100 to 500 CVs per vacancy. Our own estimate, not a figure from the plan and still to be measured: up to about three calls per application (one to list its attachments, then two when the CV is fetched: one for a fresh link and one for the download), plus a few calls to find the vacancy and to read the list in pages of 100. That is roughly 1,500 calls for 500 applications. The plan estimates 1 to 3 minutes to read the list and 5 to 10 minutes to fetch the files. Both figures are estimates and will be measured.

**What it reads.** The resource and field names below are taken from Oracle's public REST documentation. They are **still to be confirmed on your test environment** (section 4). Data calls use the path `/hcmRestApi/resources/11.13.18.05` and the header `REST-Framework-Version: 4`. Two kinds of call go elsewhere. A file fetched by its `FileUrl` comes from Oracle's content repository: Oracle's documentation describes `FileUrl` as a path that starts with `/content/conn/FusionAppsContentRepository/`. And if you ask us to use OAuth, the token comes from your identity domain's token address.

| Step                                    | Oracle resource                                                                                            | What Parallax asks for                                                                                                                                                                  |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Find the vacancy                        | `recruitingJobRequisitions`, found by requisition number (`findByRequisitionNumber`)                       | `RequisitionId`, `RequisitionNumber`, `Title`, `StateName`                                                                                                                              |
| Count its applications                  | `recruitingJobApplications` for that requisition, one row, with `totalResults=true`                        | Oracle's estimated total only                                                                                                                                                           |
| List its applications                   | `recruitingJobApplications` for that requisition, 100 at a time, in ID order                               | `JobApplicationId`, `CandidatePersonId`, `ConfirmedFlag`, `DisqualifiedFlag`, `InternalFlag`, `StateName`, `PhaseName`, `JobApplicationDate`, `LastUpdateDate`                          |
| List the attachments of one application | `recruitingJobApplications/{application}/child/attachments`                                                | `AttachedDocumentId`, `CategoryName`, `DatatypeCode`, `FileName`, `UploadedFileLength`, `DmDocumentId`; also, to confirm: the content type, the version number and the last update date |
| Fetch the CV file                       | The same attachment: a download link Oracle returns with it, or its `FileUrl`, or its `FileContents` field | The file itself, up to 10 MB                                                                                                                                                            |

The least certain points are the `Title` field and the way to download the file. Only `FileUrl` and `FileContents` are documented for this resource, so the checks in section 4 choose the download method.

- **Which applicants.** Active applicants only: confirmed, not withdrawn, not disqualified. Applications made before the date your career site began telling applicants about AI screening are skipped. Applicants who are filtered out are counted, never stored.
- **Which file.** Only attachments that are files, in the categories you tell us mean "CV" (question 14). If there are several, the newest one.
- **What it does not ask for.** No candidate names, e-mail addresses or phone numbers. No candidate profile rows (education, experience, languages, licences, work preferences). No call to the candidate resource (`recruitingCandidates`). No career-site or recruiter-screen resources (`recruitingCE*`, `recruitingICE*`, `recruitingUIJobApplications`). If the checks show that many CVs sit only on the candidate profile, we will come back to you before reading anything more.
- **Two honest notes.** `CandidatePersonId` is a number, not a name; Parallax uses it only to recognise the same person on the same vacancy again. An attachment's file name often contains the applicant's name; Parallax keeps the file name only with the stored CV and removes it when the CV is erased.
- **What it keeps.** The CV file, in Parallax's own database on Render in Frankfurt, and the requisition number and ID of each linked vacancy (the number is also written to the audit trail). Oracle's application and attachment IDs are kept only while an import is running, and the person ID is never stored as it is. Afterwards only scrambled values (keyed hashes) remain, so Parallax can tell "already imported" and can make sure an erased candidate does not come back on the next Refresh.
- **Where the CV text goes next: to an AI company, which may be outside the EU.** After a CV is copied, Parallax analyses it with AI, as it does for an uploaded CV. For that it sends the text of the CV to the one AI company the Parallax administrator has switched on. The list is fixed: Google, OpenAI, Anthropic, Z.ai, Sakana Fugu, NVIDIA. Parallax masks the name, e-mail address, phone number and links first, and it does not send the file itself; the masking does not catch everything in free text. The text leaves the EU unless the active company's account is set up for EU processing. A setting (`requireEuAi`) refuses an import from Oracle unless the active AI company processes in the EU. It is on by default. Whether it may be switched off is for the **DPO** to decide: **OPEN**. The data-processing agreements and transfer assessments for the AI companies are not done yet either.

## 2. What we need from you to switch it on

Set-up in Parallax is one form in the admin panel. A Parallax administrator pastes three things, ticks one box and clicks **Activate**. Parallax then checks the address, stores the password encrypted, makes one test call and, if it passes, switches the import on. There is nothing to install on your side. Oracle's API has no single "API key"; it needs an account, which is why there are two fields for it.

| What the administrator enters                                                           | What we need from you                                                                                                                                                 |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Oracle API address**                                                                  | The address of your production environment, for example `https://xxxx.fa.em2.oraclecloud.com`. Parallax accepts only `https` addresses that end in `.oraclecloud.com` |
| **User name**                                                                           | A dedicated integration account, used by Parallax only. Not a person's account                                                                                        |
| **Password**                                                                            | That account's password. Parallax stores it encrypted, never shows or logs it, and sends it only to the saved Oracle address                                          |
| **Tick-box:** "Applicants on our Oracle career site are told that AI assists screening" | Whether this is true today, and the date the text went live (question 22). Applications from before that date are not imported                                        |

**What the account must be allowed to read.** Through the REST API: job requisitions (to find one by its number), the job applications of a requisition, the attachments of those applications, and the attached files. Reading only: no right to create, change or delete, and nothing outside Recruiting. The attached files may be served from Oracle's content repository and not from the REST path (the `FileUrl` note in section 1). So the account needs read access to the files there too, and any network rule you set must allow that path. Which right that is, we confirm on your test environment. You know the role and privilege names; please tell us which ones you give it (question 7).

**Go-live condition: limit what the account can see.** The account must see only the recruiting organisations that are in scope for Parallax, and it must not see confidential vacancies. We need your written confirmation of this before the import is switched on in production.

Why this matters: Parallax signs in to Oracle with this one account for every recruiter. It cannot know what each recruiter may open in Oracle. By the owner's decision there is no approval step: any recruiter who can edit a Parallax vacancy can type any vacancy ID and import it. With Parallax's default setting, that is every recruiter and team lead. So whatever the account can see, each of them can copy. The security review rated this risk critical. The owner accepted it for the trial on three conditions, and your limit on the account is the first. The other two are on our side: every lookup, link, unlink and import is written to the audit trail with the requisition number and who did it, and lookups are rate-limited; and approval by a team lead is a setting that can be switched on later.

**Password policy and expiry date.** Please tell us the rules for this account's password and the date it expires (question 6). The form has a field for the expiry date, and Parallax shows a warning before it. An expired password stops every import. When the password changes, a Parallax administrator pastes the new one (**Replace password**).

**How to hand over a password or secret.** Please do not put any password, client secret or private key in your answers to this note, in e-mail or in chat. This covers the production account, the test account and any OAuth secret. Give them only to the person the programme owner names: the Parallax administrator who pastes the production account into the form, and the person who runs the checks in section 4 with the test account. No one is named yet. Use a secure channel that we agree with you first (question 35).

**One synthetic test vacancy.** On your test environment we need one vacancy made for this purpose, with invented applicants only and no real people, plus a test integration account. About 15 to 20 invented applicants would do. It helps if they include: PDF and Word (.docx) CVs; one old Word (.doc) file; one applicant with a CV and a cover letter; one who replaced the CV; one who applied without a file; one whose CV is only on the candidate profile; one withdrawn; one disqualified; one who did not finish applying; one internal applicant; one deleted or anonymised after applying. The approved plan covers one synthetic vacancy only, so we do not ask for a second, confidential one. For the "no access" check (check 10 in section 4) we ask you instead to take the test account's access to this one vacancy away for a short time, if that is practical. Question 31 asks whether you will create the vacancy and the account, who does it and by when.

## 5. What Parallax will not do

- **No writes to Oracle.** No create, change or delete. No score, note or state change is written back. An application's state in Oracle is used only to decide whether to copy the CV; it never becomes a hiring decision in Parallax.
- **No scheduled polling.** No nightly or hourly job. Every call follows a click by a recruiter or an administrator.
- **No browsing of your vacancies.** Parallax never lists or searches your vacancies. It reads one vacancy at a time: the one whose ID a recruiter typed. That first read (the number, title, state and Oracle's estimated count of applications) happens before any link exists; the link is saved only when the recruiter clicks **Start**. So a recruiter can look up any vacancy the account can see, linked or not. That is why the limit on the account in section 2 is a go-live condition. The connection test (**Activate**, **Test again**) is one small read that is not tied to any linked vacancy. It checks that the account works and can see at least one vacancy, and it keeps only the result.
- **No storing of applicants who were filtered out.** Withdrawn, disqualified, unconfirmed and too-early applicants, and applicants without a CV file, are counted. Nothing else about them is kept.
- **No names, e-mail addresses or profile rows** are requested, and Oracle's application and attachment IDs are not kept after an import ends.
- **No connection from any environment other than production.** The import can be activated only on the production Parallax service, where one deploy switch (`ORACLE_IMPORT_ENABLED`) is set. That switch is set only after the written approvals at the top of this note. Development and test copies of Parallax cannot connect to any Oracle environment, production or test; their tests use a pretend Oracle inside the test code. The only thing that touches your test environment is the hand-run script in section 4.
